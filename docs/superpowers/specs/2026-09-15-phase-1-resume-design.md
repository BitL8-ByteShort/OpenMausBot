Status: written Sep 15, 2026 after parts 1–3 were built. Part 4 as listed in the gap analysis §17 is six items; three of them are satisfied by parts 1 and 2 as built, and this document says which, with the file that proves it, so nobody rebuilds them. ## Remainder (specified, not built)

1. **`PROGRESS.md` recitation.** A per-task file the harness maintains with no model call: the goal (the thread's first user message, 300 characters) and the next step (the last digest's reply line). Recited into the turn text only when it is far from the end of the context: on the first turn after a compaction and every tenth turn of a thread past ten turns. Metric: T5 unchanged; a thread of 30 turns whose task changes at turn 3 still answers the turn-3 goal at turn 30 (a new scorecard task). Engines: full everywhere (turn text). Not built today because T5 already answers correctly at ten turns and the value only shows past that length, which the scorecard does not yet run.
2. **Driver-owned resume cursor and restart reconciliation.** The cursor becomes an opaque value the driver mints (session id plus the last message id and turn-boundary id) and the harness stores without reading; on restart, a thread whose last turn was cut mid-way shows "continue where you left off" and the next turn resumes from the last boundary; a steer never creates a turn boundary. Engines: Claude and Codex full (session ids), pi and ACP degraded (session ids where the agent gives one, else the replay), HTTP family n/a (replays every turn). Metric: a restart-and-continue scorecard task (start T5, kill the harness at turn 5, restart, send turn 6; correct when the count is 600 and no replay row appears on Claude/Codex). This is a driver contract change across six families and is the largest remaining piece.
3. **The five-section description contract on every harness tool, linted.** Each tool description carries "What it does / When to use / When not to use / Do not use for / Examples"; a test parses `AGENT_TOOLS` and fails on a missing section. Under deferred tool loading (Phase 2) the description is the selection API, so this lands with Phase 2's `search_tools`, where it is measured (tool-choice accuracy on the bench), rather than as a text-only change now.

## Why the remainder waits

Each remaining item changes what every engine is told or how every driver resumes, and none has a scorecard task today that would show it working or failing. Parts 1–3 shipped only what the scorecard and the recall set could measure; part 4's remainder gets its tasks first (the 30-turn goal task, the restart task, the tool-choice bench), then the code, in that order.
