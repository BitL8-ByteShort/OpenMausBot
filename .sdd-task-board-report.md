# Task board core — Task 3 report (the dispatcher tick)

## What was implemented

**In `server/task-board.ts`** (the two functions the previous unit deliberately left for this one, plus one the plan calls out mid-Task-3):
- `heartbeat(id)` — bumps `heartbeat_at`/`updated_at` to now for a task that is currently `running`; throws `cannot heartbeat a task that is not running: <status>` otherwise. A crashed-and-reclaimed task cannot be heartbeated back to life by accident — it has to go through `setStatus(..., "running")` again, which is the reclaim path.
- `staleRunning(olderThanMs)` — running tasks whose `heartbeat_at` is older than the given value. Despite the parameter name (carried over from the plan's own interface), it takes an **absolute cutoff timestamp**, not a duration — the dispatcher calls it as `staleRunning(now() - staleAfterMs)`, matching the plan's own Task 3 pseudocode. Documented this explicitly in the doc comment since the name alone is misleading.
- `attachThread(id, threadId)` — the plan's Task 3 Step 3 explicitly calls for this: after the dispatcher claims a task (`setStatus(id, "running")`), recording which thread it ran in cannot reuse `setStatus(id, "running", { threadId })` a second time, because `running → running` is correctly not a legal transition (self-transitions were never widened into `TRANSITIONS`, per the plan's own warning). `attachThread` is a dedicated writer that updates `thread_id`/`updated_at` without touching `status`.

**`server/task-dispatcher.ts`** (new): `createDispatcher(options): Dispatcher` with `{ tick, start, stop }`, matching the plan's produced interface (`DispatcherOptions`, `TICK_MS = 30_000`, `DEFAULT_STALE_AFTER_MS = 180_000`, `DEFAULT_MAX_ATTEMPTS = 3`). One `tick()` does, in order:
1. **reclaim** — every `staleRunning(now() - staleAfterMs)` task goes back to `ready`.
2. **give up** — every task (in `ready` or `running`) with `attempts >= maxAttempts` is moved to `blocked` with a reason matching `/N attempts/`.
3. **promote** — every `promotable()` task (todo, no unfinished parent) becomes `ready`.
4. **claim** — `ready` tasks are claimed up to `maxRunning - (current running count)`; each claim calls `options.dispatch(claimed)`; a `null` result puts the task back to `ready` without consuming a slot (the claim still counted as an attempt); a truthy result calls `attachThread` and consumes a slot.

`start()`/`stop()` and the `ticking` re-entrancy guard mirror `RoutineManager` in `server/routines.ts` (`this.timer = setInterval(...); this.timer.unref?.()`, `if (this.ticking) return; this.ticking = true; try { ... } finally { this.ticking = false; }`) — a slow in-flight `dispatch()` cannot let a concurrent `tick()` call double-claim.

- **Ordering matches the brief's own framing exactly**: reclaim → give up → promote → claim, each as its own labeled block with a comment explaining *why* it must come before the next step (not just *what* it does) — reclaim before the cap is measured, give-up before a cursed task can consume a slot, promote before claim so a task doesn't wait a full `TICK_MS` after its last parent finishes.

## Concerns

1. **The give-up-scans-`running`-too decision (disagreement #1) is a real design call, not just a typo fix**, and it has a sharp edge: in the live system, a legitimately healthy, actively-heartbeating task whose `attempts` counter happens to sit at `maxAttempts` (e.g. because a bot crashed and was reclaimed twice before finally getting a stable run going on its third claim) will be force-blocked by the very next tick even while it is making real progress and heartbeating normally — reclaim only protects against a *cold* heartbeat, and give-up as I've written it does not check heartbeat freshness at all before blocking a `running` task. Under the dispatcher's own claim-time guard (`if (task.attempts >= maxAttempts) continue`), this specific shape (claimed while already at the cap) should never arise through the dispatcher's own claim path alone — it can only happen via a `setStatus` call from outside this tick (a future Task 4/5 HTTP route or agent tool, or `maxAttempts` being lowered live). Whoever builds Task 4/5 should decide deliberately whether "already-running work gets force-blocked the moment its historical attempt count reaches the cap" is the intended production behavior, or whether give-up should instead only ever act on `ready` and rely on reclaim to first surface a truly-dead `running` task before blocking it. I chose to satisfy the plan's own test literally rather than silently rewrite that test's expectations, but this is exactly the kind of judgment call the brief asked me to surface rather than bury.
2. **`staleRunning`'s parameter name (`olderThanMs`) is misleading** — it reads as a duration but is used, both in the plan's own pseudocode and my implementation, as an absolute cutoff timestamp (`now() - staleAfterMs`). I kept the plan's exact parameter name for interface fidelity but flagged this loudly in the doc comment. A future caller reading only the signature (not the comment) could pass a duration by mistake.
3. **No test exercises `start()`/`stop()`/the real `setInterval` path** — only `tick()` is called directly in every test, per the plan's own test file. `start`/`stop` are implemented to the same shape as `RoutineManager` (`timer.unref?.()`, idempotent `start()` via `if (timer) return`, idempotent `stop()` via `clearInterval` + null-out) but are otherwise unverified by this unit's test suite. Flagging for whoever wires `boardDispatcher.start()` into `server/index.ts` in Task 4.
4. **Emit payload kinds (`"board.reclaimed"`, `"board.gave-up"`, `"board.promoted"`, `"board.claimed"`) are my own naming**, not specified anywhere in the plan's `DispatcherOptions` (`emit?: (payload: { kind: string; task: BoardTask }) => void` gives no enum of kinds). No test asserts on `emit` at all — I added the calls because Task 4's `bus.publish(payload)` wiring will need *some* event stream, but the exact string values are an invented convention that Task 4's author should feel free to rename before it ships anywhere user-visible.

## The capability rule — what I actually implemented

The plan states the rule ("only dispatch to a bot whose driver can actually run an unattended turn") but the repo has no field literally named "can run unattended." I traced it to `shared/approval-mode.ts` / `server/index.ts`'s `approvalModeForTurn(bot, peerInitiated)`, which resolves a bot's *effective* approval mode (accounting for `approvalGrant` two-phase confirmation and `supportsApprovalMode(driverKind, mode)`). Its own doc comments describe exactly this property: `autoApprove`/`"auto"` mode is "the bot approves its own tool permissions and keeps working instead of stopping to ask" — every other mode (`ask`, `edits`, `full`, `custom`) either always asks or asks for anything outside a narrow edit-acceptance carve-out. Since a board dispatch happens with nobody at the keyboard, only `approvalModeForTurn(bot) === "auto"` is safe; anything else would leave the task stuck on its first permission card forever. Implemented as a single guard in the dispatcher's `dispatch` callback in `server/index.ts`, with a comment explaining the reasoning inline. Unassigned tasks (`assigneeBotId === null`) are declined by the same callback (`return null`) rather than guessed at; a human assigns one later via `PATCH /api/tasks/:id`.

## The give-up concern — ruling and fix (commit `2afe96d3`, before Task 4/5 work)

Confirmed the concern is real: `attempts` counts attempts **started**, not attempts **failed** — `setStatus` bumps it on every entry to `"running"`, including the entry that is currently, successfully in flight. The previous unit's give-up pass scanned `listTasks({ status: ["ready", "running"] })`, so a task on its final allowed attempt — legitimately running right now, possibly about to succeed — carried `attempts === maxAttempts` and got force-blocked out from under itself.

**Ruling:** give-up must only ever look at `"ready"` tasks — a task that has already been reclaimed (by the stale-heartbeat pass, earlier in the same tick, or an earlier one) and is asking for *another* attempt. That is the only point at which "no progress" is an established fact. A currently-running task either finishes on its own or eventually goes stale and comes back as `"ready"`, where give-up then catches it before the next claim. Implemented by narrowing the give-up loop's status filter from `["ready", "running"]` to `["ready"]" and rewriting the comment to explain why `"running"` must not be scanned.

I also had to correct the *existing* test that encoded the buggy behavior (`"blocks a task that has burned through its attempts instead of looping"`, in `server/task-dispatcher.test.ts`, committed by the previous unit): it drove a task through three ready→running cycles and asserted the *final*, still-`"running"` state got blocked. Under the fix that assertion is wrong (a healthy running task must not be blocked), so I added one extra `setStatus(id, "ready")` to the scenario (representing the reclaim after the 3rd failed attempt) so it exercises the case give-up is actually supposed to catch, and added a new test for the case it must not catch.

# Task board core — the crash-recovery gap (heartbeat + completion) report

Branch: `feat/task-board-core` (worktree `/Users/omkar/Desktop/openmaus/OpenGrokBot-taskboard`), on top of `2d68308b`.
Scope for this unit: the one gap Task 4's report flagged as its top concern — nothing heartbeats a dispatched task's turn, and nothing settles it on completion, so a task whose turn succeeds still goes cold, gets reclaimed, and eventually blocked after ~9 minutes.

## What was wired

**New module `server/task-turn-watch.ts`** — `createTaskTurnWatch(): TaskTurnWatch` with `{ watch(taskId, threadId), handle(event), stopAll() }`. Deliberately kept separate from `task-dispatcher.ts` (whose own header says it owns "the tick that turns board storage into a working queue" — reclaim/give-up/promote/claim) since this is a different concern: reacting asynchronously to a turn's own lifecycle after it has already been claimed and dispatched, not a periodic tick.

- `watch(taskId, threadId)` — called once, right after a board dispatch's `startTurn` call resolves. Records `threadId -> taskId` and immediately heartbeats (covers the gap between the claim and the turn's first real event; the claim itself already stamped `heartbeat_at` via `setStatus(..., "running")`, so this is redundant-but-harmless defense in depth).
- `handle(event)` — fed every runtime event on the bus. Looks up the task by `event.threadId`; if none is watched, no-ops (cheap enough to call unconditionally for every event). For a watched thread: `"turn.completed"` → `settle(ok, reason)`; `"session.exited"` → treated as a failure too (a driver can exit without ever emitting `turn.completed` — same reason `server/index.ts`'s memory-journal subscriber folds on both events); every other event type (`item.started`, `item.completed`, `content.delta`, `thread.token-usage.updated`, `turn.retrying`, `request.opened`/`resolved`, `session.started`, non-fatal `runtime.error`, …) → `heartbeat(taskId)`.
- `settle(threadId, ok, reason)` — removes the watch entry, then `setStatus(taskId, "review")` on success or `setStatus(taskId, "blocked", { blockedReason: reason })` on failure. Both `heartbeat()` and `setStatus()` calls are wrapped in try/catch and swallow errors: if the task already moved on (reclaimed by a stale sweep and possibly re-dispatched under a fresh attempt/threadId, or a human touched it via `PATCH /api/tasks/:id`), the stale signal is simply too late to matter — it must never force a transition onto a task the board has already moved past. This does not touch `TRANSITIONS` in `task-board.ts`; every transition still goes through the existing legal-move table.
- `stopAll()` — clears the whole map, no settling. For shutdown/tests; there are no timers to clear because there are none (see next section).

**Wired into `server/index.ts`** (in the existing board-dispatcher block, ~line 5958 on):
- `import { createTaskTurnWatch } from "./task-turn-watch.ts";`
- `const boardTurnWatch = createTaskTurnWatch();` plus one `bus.subscribe` that first applies the same `shouldIgnoreProviderEvent(event)` guard every other terminal-state listener on this bus already applies (the `delegationWatch` subscriber's own pattern), then calls `boardTurnWatch.handle(event)`. Without that guard, a resumable driver's non-terminal `session.exited` (no `turnId`, bot/group still busy — the exact case `shouldIgnoreProviderEvent` exists to filter) would have been misread as "the turn ended" and force-blocked a task that was still actually running.
- Inside the existing `dispatch: async (task) => {...}` callback, right after the existing `appendDecision(...)` call and before `return { threadId: runThread.threadId }`: `boardTurnWatch.watch(task.id, runThread.threadId);`.

Net diff: `server/index.ts` +29/-0 lines. No other file in `server/index.ts` was touched — the routes, boot wiring, and capability-rule guard from the previous Task 4 unit are all untouched.

## Which signal drives the heartbeat, and why it's honest

Primary and *only* signal: the harness's own `RuntimeEvent` bus (`server/contracts.ts`'s `RuntimeEvent` union, `server/index.ts`'s `bus`) — the same stream every other terminal-state listener in this file already watches (`delegationWatch`, the stall `watchdog`, the memory-journal boundary). `item.started`/`item.completed`/`content.delta`/`thread.token-usage.updated`/`turn.retrying`/`request.opened`/`request.resolved`/`session.started` only fire while a real provider process is actually producing something — that is what makes it honest evidence of life, as opposed to a clock that ticks whether or not anything is actually happening.

**Deliberately no interval, anywhere.** I considered pairing the event-driven heartbeat with a bounded `setInterval` backstop (for the case a single tool call runs quietly for a while) and rejected it after tracing through what it would actually do to the crash-recovery invariant this unit exists to protect: a `setInterval` created at `watch()` time and cleared at `settle()` time is scoped correctly to "a dispatch happened", but its *ticks* are not evidence of anything — it would keep calling `heartbeat()` on a fixed schedule regardless of whether the provider process is still alive. A turn that wedges silently (the process hangs without ever emitting `session.exited` or `turn.completed` — which, note, is indistinguishable from "the whole Node process died" from this module's point of view, since a real process crash *also* just stops emitting events forever) would keep looking alive to `staleRunning` for as long as the interval kept firing, i.e. forever, since nothing but a real terminal event or an external `stopAll()` would ever clear it. That is exactly the failure mode `staleRunning`/reclaim exists to catch, and exactly what the brief's "a blind timer that ticks regardless of whether the turn is alive is not honest evidence" is warning about. So: pure event-driven, no timer to leak, and required test 4 ("no leaked interval or listener") is satisfied trivially on the interval half and by an explicit test on the listener half (see below).

**Known tradeoff, flagged rather than hidden:** with `DEFAULT_STALE_AFTER_MS = 180_000` (3 minutes, set by the previous unit) and no interval backstop, a single tool call that legitimately runs silently for longer than 3 minutes with no intervening `RuntimeEvent` at all would get its task reclaimed out from under a turn that is still actually working. This is a pre-existing tension between this board's aggressive stale threshold and the harness's separate stall `watchdog` (default 20 minutes, "an hour-long turn that keeps streaming is never touched") — not something introduced by this unit, and not something I was asked to retune. Noted under Concerns.

## How completion and failure are detected

- **Success:** `turn.completed` with `ok === true` → `setStatus(taskId, "review")`. Per the plan, `review` is the default terminal state for bot-completed work — nothing silently disappears into `done`; a human accepts it later via the existing `PATCH /api/tasks/:id`.
- **Failure:** `turn.completed` with `ok === false` → `setStatus(taskId, "blocked", { blockedReason: event.stopReason?.trim() || "the bot's turn ended without success" })`. `session.exited` (no matching `turn.completed` ever having arrived) → same, with `blockedReason: "the bot's session exited before the turn finished"`.
- Both go through `task-board.ts`'s existing `setStatus`, so the existing legal-transition table (`running → review | blocked | ready`) is the only thing that can ever move a task — this module adds no new statuses and widens no transition.

## How the crash path was proven to still reclaim

Two angles:
1. **Unchanged reclaim/give-up/promote/claim logic.** `task-board.ts`'s `staleRunning`/`heartbeat` and `task-dispatcher.ts`'s tick are byte-for-byte untouched by this unit (`git diff --stat` shows only `server/index.ts`, `server/task-turn-watch.ts`, `server/task-turn-watch.test.ts` changed — no diff against `task-board.ts` or `task-dispatcher.ts`). The safety net this unit was told not to weaken was never touched.
2. **New integration test** (`server/task-turn-watch.test.ts`, "a crashed turn (heartbeats simply stop arriving) is still reclaimed by the dispatcher tick"): claims a task, `watch()`es it, feeds exactly one `item.started` event (the last thing the "process" does before "dying" — no more `handle()` calls ever follow, simulating the crash), advances a fake clock 181s past the default 180s `staleAfterMs`, then runs a real `createDispatcher(...).tick()` against the same board file. Asserts `dispatch` gets called again (the task was reclaimed and re-claimed) and `attempts` is now `2` (one original claim + one reclaim). This exercises the actual `task-dispatcher.ts` reclaim path, not a mock of it — proving the new watch module cannot mask a dead turn from the existing dispatcher.

# Fix round 1 — a low-frequency keepalive alongside the event-driven heartbeats

Coordinator finding: the round-1 implementation above was purely event-driven. ## Concerns (updated)

1. The original round-1 "quiet turn may be spuriously reclaimed" concern is now closed by this fix — superseded, not still open.
2. `keepaliveMs` and `staleAfterMs` are duplicated as *concepts* between `task-dispatcher.ts` (which owns the real `staleAfterMs` used by `staleRunning`) and `task-turn-watch.ts` (which now derives its own keepalive cadence from a *second* `DEFAULT_STALE_AFTER_MS`-defaulted value). In `server/index.ts` both are constructed independently (`createBoardDispatcher({...})` and `createTaskTurnWatch()`), and today they agree only because neither call site overrides the default. If a future change ever configures the dispatcher's `staleAfterMs` from `cfg` without also passing the same value into `createTaskTurnWatch({ staleAfterMs })`, the keepalive's margin against the real stale cutoff would silently drift. Flagging for whoever eventually makes `staleAfterMs` configurable — it should be threaded to both constructors from one place, not two.
3. `result` on a successful `review` transition is still left `null` (unchanged from round 1, see original Concern 2 above) — not something this fix round was asked to address.
