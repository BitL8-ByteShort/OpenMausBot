# Quota-switch: continue on another engine — implementation report

Branch: `feat/quota-switch` (worktree `/Users/omkar/Desktop/openmaus/OpenGrokBot-quota`), off `origin/main` 536b7893.

## What was built

**Part 1 — the quota card (`server/quota-switch.ts`, new module)**

- `maybeRaiseQuotaCard(deps, bot, threadId, errorMessage)` — the single entry
  point server/index.ts calls from `case "runtime.error":`. It owns the
  quota decision itself (calls `classifyError({ text: errorMessage })` from
  `server/drivers/retry.ts` and bails unless `reason === "quota"`), then:
  - looks up `deps.instances()` (wired to `registry.instances()`), filters
    out the bot's current `modelSelection.instanceId`, caps at 3;
  - bails (returns `null`) if there are no alternatives, or if a card is
    already pending on this thread (`pendingQuotaThreadIds`);
  - pushes one harness-native options card via `store.appendMessage` —
    title `"<Current engine> is out of quota"`, subtitle asking to
    continue on another engine, options = alternative display names +
    `"Not now"`. Deliberately carries **no `card.tool`** — see below.
  - records the pending offer (`pendingQuotaCards`, keyed by `requestId`,
    and `pendingQuotaThreadIds`, keyed by `threadId`, for the one-card-per-
    thread rule) — same in-memory-only pattern as `peer-approval.ts`.

- `resolveQuotaSwitch(deps, requestId, message)` — called from both
  `/api/bots/:id/respond` and `/api/threads/:id/respond`, right next to the
  existing `resolvePeerComms(...)` intercepts, in the same
  `if (store.messagesFor(...).some(...) && resolveX(...))` shape. Returns
  `false` immediately if `requestId` isn't one of ours (so peer/provider
  cards keep routing normally). If it is:
  - settles the card synchronously (`answered: "answer"`,
    `answeredText: <chosen label or "Not now">` — matches how every other
    tool-less "question" card remembers its reply, per
    `server/index.ts`'s `answerRequest`);
  - if the message matched one of the offered engines, kicks off (fire-
    and-forget, `void`) the actual switch + re-dispatch;
  - "Not now" (or anything else — e.g. the card being dismissed with X)
    settles the card and does nothing further.
  - Returns `true` synchronously either way, so it slots into the same
    `if (...) return` chain `resolvePeerComms` already sits in without
    forcing the two respond endpoints to become any more `async` than they
    already are.

**Why the card carries no `tool`**: I read `src/lib/card-answer.ts` before
designing the wire shape. `answerResponse(card, answer)` branches on
`card.tool`: if set, EVERY non-"Deny" press collapses to `behavior: "allow"`
— fine for a 2-outcome permission card, but it would erase which engine was
picked. Leaving `tool` unset makes the client treat it as a question
(`ChatView.tsx`'s `m.card?.requestId && m.card.tool` → `ApprovalCard`,
otherwise → `OptionCard`), so `behavior` is always `"answer"` and the
pressed label reaches the server verbatim as `body.message`. That is the
only way a card offering more than two choices can carry which one was
picked.

**Picking a valid model on the target engine** — `pickSelection` reuses
`selectDefaultModelSelection` from `server/default-model-selection.ts`
verbatim, handing it a one-element array built from the chosen instance's
freshly-awaited `snapshot()`. If the instance is available it returns that
instance with its own default model; if not (torn down between the card
being raised and answered), it returns the empty selection
`selectDefaultModelSelection` already uses for "nothing to offer" — no new
"is this a valid model" logic was written.

**Switching + re-dispatch** — on a valid selection: `store.patchBot` +
`store.patchTask` (same two calls the `/api/bots/:id/model` PATCH endpoint
makes), an activity chip ("continuing on <Engine> after hitting quota"),
then the last user `kind:"text"` message on `store.activePath(threadId)` is
re-sent through `deps.dispatch(botId, threadId, text)` — wired in
`server/index.ts` to `startTurn(botId, text, { threadId })`, so the
re-launched turn gets the exact same admission/lifecycle path any other
message does, and `buildTurnContext`'s existing "fresh engine" replay
(`engineIsFresh`) automatically carries the prior history across, since
nothing here is new — the feature this task's Part 2 improves.

**Part 2 — tool history in the replay (`server/turn-context.ts`,
`server/index.ts`)**

- `formatToolActivityLine(tool: { name, ok? })` — new pure, exported helper
  in `server/turn-context.ts`. Formats `[ran: <name lowercased> — ok]` or
  `… — failed]` (missing `ok` defaults to "ok", matching how activity chips
  already treat an absent `ok`), truncated to 120 chars with a trailing `…`.

- `server/index.ts`'s `startTurn` now builds a second, parallel array,
  `replayTranscript`, right next to the existing `transcript` (around the
  original line ~3986 the task pointed at — the `filter/slice(-40)/map`
  block). It is identical to `transcript` except its filter also admits
  `kind: "activity"` messages that carry a `tool`, and its `.map` renders
  those as `formatToolActivityLine(m.tool)` instead of `transcriptText(...)`.
  It reuses the exact same `slice(-40)` cap, so tool lines cannot make the
  replay grow unbounded — they compete with text turns for the same 40
  slots rather than adding to them.
  - `transcript` (text-only) is **untouched** and still feeds
    `engineIsFresh(...)`, `buildRecoveryText(...)` (the resume-recovery
    fallback), and the driver's own `SendTurnInput.transcript` for
    `replaysNatively` drivers (further down in `startTurn`) — exactly the
    three places the task said must not change.
  - Only the `buildTurnContext({...})` call's `transcript` field was
    changed to `transcript: replayTranscript`. Since `buildTurnContext`
    only ever reads its `transcript` argument when `!resume` (rewind /
    fresh engine / external update), a resumed turn is provably unaffected
    — confirmed by a dedicated test.

## Concerns

- The re-dispatch's fire-and-forget error path (`quotaSwitchBus.dispatch`'s
  `.catch`) posts a plain activity chip on `startTurn` failure (mirroring
  `drainQueuedSends`'s own fallback) rather than surfacing a fresh card —
  if the re-dispatch itself fails (e.g. the newly-chosen engine is also
  down), the person sees an error chip but no obvious retry affordance
  beyond typing again. This matches the task's scope (no mention of a
  cascading second offer) but is worth a follow-up if it comes up in
  practice.
- No test exercises the actual `server/index.ts` wiring end-to-end (i.e. a
  real `runtime.error` event flowing through `bus.subscribe` into a raised
  card, or a real HTTP `/respond` call hitting `resolveQuotaSwitch`) —
  `server/index.ts` has no existing test harness for the giant
  `bus.subscribe` handler to hook into, and the task scoped tests to
  `quota-switch.test.ts` (against the module directly, via its injected
  `QuotaSwitchDeps`) and `turn-context.test.ts`. The wiring itself is
  intentionally thin (a handful of lines mirroring `resolvePeerComms`'s
  existing, already-tested-elsewhere pattern), which is the reason I did
  not add an index.ts-level test myself.

## Fix round 1

A review of the above found three Important issues plus two small items.
All five are fixed. Nothing else from the review was touched — boot-time
stale-card cleanup and the duplicated transcript block in `server/index.ts`
were both explicitly called out as deferred and left alone.

### Finding 1 — the card could offer an unavailable engine

`maybeRaiseQuotaCard` used to filter candidates only by
`instanceId !== currentInstanceId`; availability was checked later, only
once the user clicked. Fixed by checking `instance.snapshot()` for every
candidate **when the card is built**, keeping only those whose
`snapshot.state === "available"` — the exact bar
`selectDefaultModelSelection`'s own "pick anything available" fallback
already uses, so what's offered and what `pickSelection` will later accept
are provably the same test. This makes `maybeRaiseQuotaCard` `async`
(`Promise<Message | null>`); its one caller in `server/index.ts` now reads
`void maybeRaiseQuotaCard(...)` — raising the card was always fire-and-
forget from the runtime-event handler's point of view, so nothing else
about that call site changed.

The click-time check in `pickSelection`/`switchAndRedispatch` stays as the
second line of defence (state can still change while the card sits open),
but its failure is no longer silent: `switchAndRedispatch` now posts an
activity chip ("`<Engine>` is no longer available — nothing switched.")
before returning, for both "instance vanished from the registry entirely"
and "instance still configured but no longer available" (`pickSelection`
returning the empty selection).

Covering tests (`server/quota-switch.test.ts`):
- `never offers an engine that is unavailable when the card is built` —
  Codex unavailable → card options are `["Grok", "Not now"]`, no Codex.
- `raises no card when every alternative is unavailable`.
- `does not switch when the chosen engine goes unavailable between raise
  and answer, and says so` — Codex is available when the card is raised,
  goes unavailable before the answer arrives; asserts `modelSelection`
  stays on Claude, `dispatch` is never called, and a
  `"...no longer available..."` chip (`ok: false`) is posted.

### Finding 2 — the card exposed a free-text input

Per the ruling, the card stays non-blocking (the composer is deliberately
left open) — only the stray input was in scope. Added
`fixedOptions?: boolean` to `OptionCardData` in `server/store.ts`
("answers must be one of `options`; no free-text reply") and to its
duplicate client-side type in `src/state/store.tsx` (the frontend does not
import the server type — `npx tsc -b` confirmed this second copy exists and
needed the same field, or the frontend build fails). Set
`fixedOptions: true` on the quota card. In `src/components/OptionCard.tsx`
the free-text `<input>` now also requires `!card.fixedOptions` to render
(alongside the existing `!card.answered && !card.tool`).

Server-side, an answer that names none of the offered engines — including
a stray free-text POST that reaches `/respond` directly, bypassing the now-
hidden input — was already routed through the same `chosen ? ... : NOT_NOW`
branch as an explicit "Not now", so no server logic changed here; added a
test to pin that this is really true: `treats an answer that names none of
the offered engines exactly like 'Not now'`.

`ios/` and `android/` were not touched, per instruction. Their own card
renderer does not know about `fixedOptions` and may still show a free-text
box beside this card's buttons; typing into it and sending answers
something that matches none of `pending.alternatives`, which the server-
side fix above already handles safely (treated as "Not now" — nothing
switches, the card just settles). This is a real, if minor, phone
inconsistency worth a follow-up ticket, not fixed here.

### Finding 3 — re-dispatch could resend the wrong message, or none

Replaced the "scan the active path backwards for any `kind:"text"` message"
at *answer* time with a `userMessageId` captured at *raise* time. In
`server/index.ts`'s `runtime.error` case, right before calling
`maybeRaiseQuotaCard`, the handler now finds the last `role: "user"`
message on `store.activePath(event.threadId)` — this is unambiguously the
message the failing turn was answering to, since nothing else can have been
appended to the thread between dispatch and this failure — and passes its
id through. `maybeRaiseQuotaCard` threads it into the new
`PendingQuotaCard.userMessageId` field.

`switchAndRedispatch` now looks that exact message up by id (never re-scans
"the last user message") and resends its raw `.text`. Since an attached
image travels as a `<attached-image path="..." name="..."/>` transport tag
embedded directly in the message's own `text`
(`server/turn-images.ts`/`startTurn` parse it back out on the way in),
resending the captured message's `text` verbatim resends its attachments
too — no separate attachments field exists on a user message to carry.

If the captured message can no longer be found (or its text is empty) when
the user answers, `switchAndRedispatch` now posts **no** "continuing on
`<Engine>`" chip; instead it posts
`"switched to <Engine>, but the message that hit quota could not be found
to resend — send it again."` (`ok: false`) and dispatches nothing. The
switch itself (`patchBot`/`patchTask`) still happens in this case — there
is no reason to also refuse using the new engine for the next message the
person types by hand.

Covering tests:
- `re-dispatches an image-only original message, tag and all` — the
  captured message's whole text is the `<attached-image .../>` tag; asserts
  `dispatch` is called with that exact tag string.
- `resends the message captured at raise time, not a newer one sent while
  the card was open` — appends a second, unrelated user message after the
  card is raised but before it is answered (the composer stays open, so
  this is a real scenario); asserts the ORIGINAL message is resent, not the
  newer one.
- `when the original message can no longer be found, posts no 'continuing'
  chip and says so instead` — blanks the captured message's text to stand
  in for "gone"; asserts no "continuing on..." chip, a
  "...could not be found to resend..." chip (`ok: false`) instead, and no
  dispatch.
- `raises no chip and dispatches nothing when there was no user message to
  capture` — `userMessageId: undefined` end to end (a bot's own turn with
  no originating user message); asserts the switch still lands but nothing
  is dispatched and no chip is asserted either way (the "not found" chip
  path and this path share the same `!original?.text` guard).
